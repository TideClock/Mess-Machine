# REVIEW A: server and safety side of docs/ACCOUNTS-SPEC.md (sections 1, 2, 6, 7, 8a, 8d, 8e, 9, 10)

1. VERDICT: build after the must-fixes. The shape is right (functions only, per-owner files, a row lock for order); the holes are in details and each has a small fix. Nothing here touches Tyler's seven decisions, except that the spec fails to honour decision 5 in one place (M5).

2. MUST FIX, ranked

M1. apply_ops checks its limits before it takes the lock, so every limit can be raced. [Certain: ran the spec's own SQL on Postgres 16, connections released at the same instant]
- 60 batches from one editor: 51 stored in 0.1 s (limit is 5 a second). Six editors' first batch at once: 6 live seats (limit 4). One batch id from 6 connections: one answer and five raw "23505 duplicate key" errors, not "its first answer again". 22 batches had an `at` earlier than the rev before them.
- Better way (ran it: 5 stored, 4 seats, identical answers, 0 out of order): right after the input checks put `perform 1 from public.messes m where m.id = p_mess for update; ts := clock_timestamp(); r := mm_private.role_in(p_mess);` then the duplicate check, rate, live seat and name check, then the rev update.
- Write the same rule over all of 2.3: "the first statement locks the row the count hangs on". The `messes` row for redeem_invite (8 members; and `update invites set uses_left = uses_left - 1 where id = x and uses_left > 0 returning`), make_invite, join_live. The caller's `profiles` row for create_mess, fork_mess, transfer_mess (200), register_sound, finish_upload (250 MB, 20 pending), vault_submit. One two-connection test per limit in 8a.
- Not enforced at all: the 20 MB per sound cap is checked against the claimed `p_bytes` only. finish_upload must delete the row and answer `too_big` unless the real size equals the registered `bytes`. Seconds and rate can never be checked in SQL, so 4.5 must say: the FLAC reader stops at the row's seconds x rate and treats every downloaded sound as hostile (a tiny file can claim hours of samples and crash every member on each open). [Likely]

M2. Any editor can stop snapshots for good with one call. [Certain: ran] `apply_ops(..., p_v := 32767)` set `messes.ops_v` to 32767. From then on save_snapshot answers `client_too_old` to every app, ops never trim, every open replays everything.
- Better way: `insert into public.config values ('ops_v_max','1')`; in apply_ops and save_snapshot `p_v between 1 and ops_v_max` else `bad_input`. A release that raises OPS_V ships a migration that raises it.
- Client twin (for the other reviewer): an unknown op in a batch whose `v` is not above mine is junk and dropped by everyone; `sawNewer` is set only when `v` is above mine. Today one `{"t":"junk"}` from an editor stops every phone uploading snapshots.

M3. "Only the owner renames" does not hold. [Certain: ran] An editor's batch `[{"t":"mess.set","f":"name","v":"x"},{"t":"mess.set","f":"name","v":null}]` was stored and broadcast: the check reads only the last name op and skips it when null. Names sent through apply_ops never meet `clean_name`, and save_snapshot lets an editor set `name` from the doc.
- Better way: `if exists (any mess.set name op) then`: every such op's `v` must be a JSON string else `bad_input`; `r` must be owner; `nm` is the last; `mm_private.clean_name(nm)` else `bad_name`. save_snapshot never writes `name`.

M4. Nothing bounds what lands in Postgres, the costly store. [Certain on the sums, Likely on Supabase's numbers]
- At the legal rate one editor writes 5 x 64 KB = 320 KB a second per mess, about 1.1 GB an hour, stored twice (mess_ops, and realtime.messages for some days), times 200 messes. Free's database is 500 MB, Pro's disk 8 GB. Trimming waits 7 days and needs a snapshot nobody has to send. 200 messes x (1 MB doc + 8 MB versions) is 1.8 GB of database per account, seven times the sound quota. open_shared is anon, unlimited, and returns the doc plus every op after doc_rev.
- Better way: (a) batch cap 16 KB. (b) `messes.ops_bytes bigint` (bytes since doc_rev): apply_ops answers `snapshot_first` when `rev - doc_rev >= 2000 or ops_bytes > 2097152`; save_snapshot resets it and deletes ops below `doc_rev - 500` on the spot (no 7 days, no pg_cron). (c) `mm_private.usage(user_id, day, op_bytes, snapshots, reports)`: 20 MB of ops a day per person, 6 labelled snapshots a minute (today one editor can push out all 8 MB of history in seconds). (d) per owner, docs plus versions at most 30 MB (`config.docs_limit`); versions 2 MB a mess.

M5. Decision 5 fails in ordinary use. [Likely: my reading of 4.5]
- "Send a sound up" uploads any `bn:` key a mess needs. A sound B got from A's mess sits in B's Library ("From shared messes"); when B uses it in a new online mess, B's phone uploads it as B's own file, and A's deletion never touches it. And "Fetch a sound" uses the cache before it looks at `src`, so a `gone` sound keeps playing from the cache and Library.
- Paste into 4.5: "A sound whose `owner` is not me is never uploaded by me. It is attached with `attach_sound(mess, key, owner, sha)`; `not_found` means its maker left and the pad reads Missing. When the server lists a sound as `gone`, delete its cache file and its 'From shared messes' Library entry before anything plays." Add both to the contract tests. `del-hand` must say a handed-over mess loses the leaver's sounds.

M6. Deletion can stop half way, and a ban leaves everything up. [Certain by reading]
- delete_account_data commits (profile gone) before the files and the auth user go. If a later step fails nobody retries, and the token still works for up to an hour with no profile behind it. "Ban in the dashboard" leaves share links and sounds live.
- Better way: one guard, used by every function and policy helper in place of `auth.uid()`: `mm_private.caller() returns uuid` gives `auth` when the uid is null, has no profile, `profiles.banned` is set, or the JWT's `amr` holds method `password` and the uid is not `config.review_user`. Table `mm_private.deletions(user_id uuid primary key, asked_at timestamptz, done_at timestamptz)` written in the same transaction as the data delete; the daily sweep finishes any row with no `done_at` (remove the folder, deleteUser). `admin_ban_user(p_user uuid, p_banned boolean)`: sets `banned`, blocks their messes, clears their share links; may_read_sound refuses a banned owner's files to others.

M7. The review password opens password sign-up to everyone. [Likely; the takeover part is Guessing, not confirmed today]
- Supabase has no "codes only" switch: `POST /auth/v1/signup` with any email and a password is live. With "Confirm email" off that is a session under an address nobody proved (beats email-locked invites, squats accounts). With it on, the attacker's password may still be on the row after the real owner signs in by code.
- Better way: "Confirm email: on" as a written step and check in 8e; the `caller()` rule in M6 makes a password session useless except for the review user; the review user is never an admin; test: a direct password sign-up cannot call `me()`.

3. SHOULD FIX

S1. Default grants. [Certain: ran] With Supabase's defaults, a table or function made in a later migration is open to anon until someone remembers the revoke, and the spec's "a default cannot be revoked" is wrong for the global one. Top of migration 1: `alter default privileges revoke execute on functions from public;` `alter default privileges in schema public revoke all on functions from anon, authenticated, service_role;` `alter default privileges in schema public revoke all on tables from anon, authenticated;` (same for sequences). Put the six policy helpers in their own schema `mm_policy`: today `authenticated` has usage on the schema holding `delete_account_data(p_user)` and held execute on it until the next revoke [ran]. deny.test should read pg_class and pg_proc, not a list of 17.
S2. Storage reads. [Likely] Whoever may read an object can mint a signed URL for it with any lifetime: free public hosting of any bytes labelled flac, and a member can publish a mate's sound. Register, upload, delete_sound, repeat leaves unlimited orphans until the sweep. Better: drop `mm_sounds_select` and `mm_vault_select`; one function `sound-urls` (the shared-sounds code, for members too) hands out 10 minute URLs; delete_sound keeps the row as `state = 'deleting'`, still counted, until the object is gone.
S3. Removed people and presence. [Certain: Supabase's page read today says the check is cached for the connection and there is no kick] Better: topic `mess:<id>:<channel_key>`; remove_member, block and take-down rotate the key; open_mess returns the topic; the policy checks the key. Presence carries only `{u, page, loop, pad, playing}`, clamped; name, colour and role come from `members()`; an unknown `u` is dropped (today a member can show any text as a name or pose as another member). Blocking should remove the person from all of the owner's messes at once.
S4. Admin reach. `is_admin()` reads every private sound of every account, which makes the privacy line "who sees it: people you share with" untrue. Narrow it to files with a pending submission or in a mess with an open report. Add `admin_open_report(p_id)` (doc and sounds; today a member-reported private mess cannot be looked at) and `admin_block_sound(p_owner, p_sha256)` (a take-down misses forks today). Put `/vault/` on its own Netlify site with a strict CSP and `textContent` only: `/m/` shows attacker-chosen names on the same origin as the admin's session.
S5. Vault. The review page must listen to and copy the same bytes held in memory, and vault_review should check the vault object's size equals the submission's `bytes`. Theft: a mess-mate can re-upload A's sound and submit it first; vault_queue should list other owners of the same sha with dates. Freeze the grant on approval in vault_sounds (`grant_version`, `body_sha256`, `granted_at`, granter uuid with no foreign key); ask Tyler whether the email is kept as proof. State that an approved sound cannot be withdrawn in the app.
S6. Edge Functions. [Certain: Supabase's keys page read today] Legacy anon and service keys end by the end of 2026; the new keys are not JWTs, and passing `verify_jwt` "doesn't authenticate the caller". So delete-account trusts only `getUser`; sweep needs a secret header (today anyone could call it); shared-sounds gets a per-token daily counter (a popular link to 250 MB of sounds is Tyler's egress bill); all three need CORS for the web pages.
S7. Stores. [Certain: Play's page read today asks for "an in-app system for reporting and blocking objectionable UGC and users"] Add `p_user uuid default null` to report_mess (column `about_user`) so a person can be reported, and `block_user(p_user uuid)` for any member, not owners only (they cannot join my messes, I leave theirs, their invites read invalid to me). Terms: 13 or older, "no tolerance for objectionable content or abusive users", reports acted on within 24 hours (Apple 1.2 reviewers look for these; [Likely]). Privacy: backups keep deleted data up to 7 days.
S8. Small ones. ops_since should refresh the caller's `mess_live.seen_at` (there is no heartbeat; a quiet editor loses the seat after 90 s). restore_version must check the version belongs to `p_mess`. open_shared says "no ids of people" but `batch.user` and `sound.owner` carry them. Invite token size is unstated: say 24 random bytes. Use built-in `sha256()` and `gen_random_uuid()`: pgcrypto sits in schema `extensions` on Supabase and breaks under an empty search path [Likely]. Sign-in code life 10 minutes, not 1 hour.
S9. Tests. As written they would not have caught M1, M2, M3 or S1. Run `supabase start` in GitHub Actions now (Docker pulls there; the APK already builds there) and run 8e steps 2 to 9 against it with its mail catcher: every [Likely] in section 2 becomes a CI check before Tyler has a project. Run the stub's migrations as a non-superuser with bypassrls, like Supabase's `postgres`. Add: the races of M1; a table-driven check that every function taking an id answers a stranger with an error and changes nothing; catalogue checks (every public function is definer with an empty search path, every table has RLS on and no client grant); a caller with a good token and no profile; a public (not private) join of `mess:<id>` hears nothing.
S10. Running costs. [Likely] Realtime counts each delivery: 4 editors at 5 batches a second is about 290,000 messages an hour, so Free's 2 million is 7 busy hours; set SEND_MS to 400 and the limit to 3 a second. Free pauses after a week idle and has no backups; keep the Pro spend cap on.

4. CUT OR DEFER (none of these weakens safety)
- The Vault (phase 6) until after the Play launch: until then deletion is simply "everything goes gone". Keep the `src` column. Saves a bucket, six functions, the review page and the grant text.
- transfer_mess and the hand-over step in both delete flows: delete with a warning; editors can Duplicate first. No store asks for hand-over.
- Email-locked and multi-use invites: single-use links only (also removes the M7 invite angle).
- The viewer role and set_role: the View share link already covers watching.
- Presence and soft locks for the first live build (risk 2 already allows it).
- Takes over 100 s: enforce 100 s and 20 MB for every kind now, drop `take_seconds` until the recorder exists. Decision 3 is met later with one config row.
- The pglite runner and the web `/` account page.

5. CHECKED AND FOUND SOUND
- All SQL in 2.1 to 2.7 loads cleanly on Postgres 16 with a stub. The row lock gives revs with no gap or repeat under 60 parallel writers. [Certain: ran]
- The new-user trigger still fires with execute revoked and no schema usage for the inserting role. [Certain: ran]
- Definer functions with an empty search path and full names; the null check on `auth.uid()`; `not_found` covering both "no such thing" and "not on it"; hashed invite tokens; a 192 bit share token; no client broadcast policy; no update policy on Storage; the broadcast in its own exception block.
- Per-owner paths are the right call for decision 5. Rows, then files, then the auth user is the right deletion order, and the fresh-code check is good.
